STEP 1 - Backend foundation (2026-11-21)
------------------------------------------------
What: FastAPI app, SQLAlchemy 2 models for the 9 tables in docs/api-contract.md, Alembic
initial migration, deterministic idempotent seed, /health, demo-session auth.
Files (backend/): requirements.txt, app/{config,db,models,deps,main,seed}.py,
app/routes/auth.py, alembic.ini, migrations/, tests/{conftest,test_health,test_seed,test_auth}.py
Design points:
- The double-booking guard is a partial unique index on appointments(slot_id) WHERE status='booked'.
- Auth: cookie "session" (httpOnly, SameSite=Lax) pointing at a row in the sessions table,
  8-hour expiry. Roles: patient, receptionist, admin.
- Seed is deterministic (random seed 42) and wipes all tables before inserting
  (see docs/known-issues.md).
How to run locally:
  docker compose up -d --wait
  cd backend && .venv/bin/alembic upgrade head && .venv/bin/python -m app.seed
  .venv/bin/uvicorn app.main:app --reload --port 8000
Checked: pytest 19 passed; ruff clean; alembic + seed twice leaves 6 doctors, 60 daily_counts,
11 appointments.

STEP 3 - Appointment lifecycle and clinic APIs (2026-11-21)
------------------------------------------------
What: book, reschedule and cancel in ONE service (backend/app/services/appointments.py), the only
code that changes appointment status. Plus doctors, free slots, guides and dashboard endpoints.
Rules: booked can move to booked (new slot) or cancelled. cancelled, completed and no_show are
final. A second booking of one slot returns 409 slot_taken (enforced by the database index, tested
with two concurrent writers). Past slots return 422. Patients only touch their own appointments.
Checked: pytest 94 passed (this includes step 4); ruff clean; grep proves no appointment status
write outside the service.

------------------------------------------------
STEP 4 - Insights API with Demo forecast (2026-11-21)
------------------------------------------------
What: GET /api/insights (receptionist and admin only). 30-day totals, cancellation and no-show
rates, history, and a 7-day forecast labelled "Demo forecast". Method: mean of the same weekday
over the previous 4 weeks of synthetic daily_counts. No machine-learning model is used and the
word Chronos never appears.
Files: backend/app/services/insights.py, backend/app/routes/insights.py, tests/test_insights.py
Checked: 19 insights tests pass; full suite 94 passed.

------------------------------------------------
STEP 5 - Assistant (local rule-based provider) (2026-11-21)
------------------------------------------------
What: provider interface (backend/app/services/assistant_provider.py), pending-action store with
explicit states pending -> confirmed | dismissed | failed (backend/app/services/assistant.py),
three endpoints, and the /assistant chat page.
Rules: the assistant only answers clinic-guide questions and proposes appointment actions. It never
changes anything itself. A proposal is stored as a pending action; only the Confirm button runs it,
through the same appointment service the normal screens use. A second confirm returns 409. Only one
pending action per user. No network or Cloudflare code exists in the backend.
Checked: 40 assistant tests; full backend suite 134 passed; ruff clean; grep finds no network code.
Known limits are listed in CONTINUE-PROMPT.md section 5.
